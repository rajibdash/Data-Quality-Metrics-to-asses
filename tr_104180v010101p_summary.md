# Summary: Data Quality Metrics — How to Assess

This document summarizes practical guidance for assessing data quality metrics. It converts the attached specification into a clear, actionable checklist and measurement guide so teams can evaluate, monitor, and improve data quality across systems.

> Note: This summary is a practical guidance document for applying common data quality dimensions and metrics. Use it as a starting point for tailoring measurements and thresholds to your specific data domains and business requirements.

## Purpose
- Provide a clear, repeatable approach to measure data quality.
- Define common data quality dimensions, metrics, measurement formulas, and sampling methods.
- Describe roles, tools, reporting, and remediation workflows.

## Scope
- Applies to structured and semi-structured datasets used for analytics, reporting, ML, and business operations.
- Focuses on operationalizing measurements at dataset, table, and column levels.

## Key Definitions
- Data Element: individual field or column value.
- Record/Row: a single logical entry in a dataset.
- Dataset/Table: collection of records with a common schema.
- Data Quality Rule: a predicate that data should satisfy (e.g., NOT NULL, within range).
- Metric: quantified measurement of one quality dimension.

## Data Quality Dimensions and Recommended Metrics
1. Accuracy
   - What: How closely data reflects the real-world values.
   - Metrics: Error rate = (# incorrect values) / (total values checked).
   - Measurement: Compare sample to a trusted reference (golden record) or business rules.

2. Completeness
   - What: Absence of required values.
   - Metrics:
     - Null rate = (# NULLs or missing) / (total rows)
     - Required-field completeness = (# rows with value) / (total rows)

3. Consistency
   - What: Agreement between related data elements and across systems.
   - Metrics:
     - Conflict rate = (# mismatched records across sources) / (total compared)
     - Referential integrity rate = (# valid foreign keys) / (total foreign keys)

4. Validity
   - What: Conformance to defined formats, types, and business rules.
   - Metrics:
     - Invalid format rate = (# values failing regex/type checks) / (total values)

5. Uniqueness
   - What: Degree to which records are not duplicated.
   - Metrics:
     - Duplicate rate = 1 - (unique_rows / total_rows)

6. Timeliness (Freshness)
   - What: How up-to-date the data is for its intended use.
   - Metrics:
     - Staleness = now() - last_update_timestamp (e.g., in hours)
     - Late arrival rate = (# late batches) / (total expected batches)

7. Reliability / Availability
   - What: Can consumers access the data when needed and with expected SLAs.
   - Metrics:
     - Availability percentage = (successful accesses / total access attempts)

8. Integrity / Lineage
   - What: Traceability of data origin and transformations.
   - Metrics:
     - Lineage coverage = (# datasets with lineage metadata) / (total datasets)

## Typical Measurement Formulas / SQL Examples
- Null rate (column col):
  SELECT COUNT(*) FILTER (WHERE col IS NULL) AS nulls, COUNT(*) AS total,
         (COUNT(*) FILTER (WHERE col IS NULL)::float / COUNT(*)) AS null_rate
  FROM my_table;

- Duplicate rate on key (id):
  WITH total AS (SELECT COUNT(*) AS t FROM my_table),
       unique AS (SELECT COUNT(DISTINCT id) AS u FROM my_table)
  SELECT (1 - u::float / t) AS duplicate_rate FROM total, unique;

- Invalid format rate (email regex):
  SELECT SUM(CASE WHEN email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$' THEN 0 ELSE 1 END) / COUNT(*)
  AS invalid_email_rate
  FROM users;

- Referential integrity:
  SELECT COUNT(*) FILTER (WHERE fk_id IS NULL OR fk_id NOT IN (SELECT id FROM dim_table)) AS bad,
         COUNT(*) AS total,
         (bad::float / total) AS ref_error_rate
  FROM fact_table;

## Measurement Process (Recommended Lifecycle)
1. Define data quality requirements per dataset and consumer (SLOs and thresholds).
2. Identify metrics and rules that map to business needs.
3. Instrument checks (SQL, validation jobs, data quality platforms).
4. Establish monitoring cadence (real-time, hourly, daily, weekly) by dataset criticality.
5. Alerting: set threshold-based alerts and escalation rules.
6. Root cause analysis and remediation workflow: ownership, fix, verify.
7. Continuous improvement: refine rules, thresholds, and sampling.

## Sampling Guidance
- For large datasets, use stratified random sampling (by partition, time window, or business key) to estimate error rates with confidence intervals.
- Capture sample size by desired margin of error and confidence (e.g., 95% CI with ±2% error).

## Thresholds and Severity Levels (Example)
- Green: metric <= 0.5% (OK)
- Yellow: 0.5% < metric <= 2% (Investigate)
- Red: metric > 2% (Action required)
Adjust thresholds per dataset criticality and business tolerance.

## Roles & Responsibilities
- Data Owner: sets SLOs, approves thresholds, owns remediation decisions.
- Data Stewards: define rules, maintain dictionaries, triage alerts.
- Engineers: implement checks and monitoring, fix pipeline issues.
- Analysts / Consumers: report quality issues and validate fixes.

## Reporting & Dashboards
- KPI dashboard per dataset with historical trend lines for each metric.
- Weekly summary emails for dataset owners listing failing checks, severity, and status.
- SLA / SLO reports for critical pipelines.

## Tools & Automation
- Examples: Great Expectations, Deequ, Soda SQL / Soda Core, Apache Griffin, Monte Carlo, data observability platforms.
- Integrate checks into CI/CD for data pipelines and pre-deployment validations.

## Example Use Cases
- ETL pipeline: measure completeness and timeliness per partition and alert on high null rates or late arrivals.
- ML features: check uniqueness, validity, and drift relative to training data.
- Master data: ensure uniqueness, referential integrity, and accuracy against golden source.

## Remediation Workflow (Suggested)
1. Alert triggers and notifies steward/owner.
2. Triage: confirm false positive vs real issue.
3. Identify root cause (upstream system, transformation bug, schema change).
4. Fix (code, process, source) and re-run checks.
5. Close incident and update runbooks and alerts if necessary.

## Practical Checklist for Getting Started
- Inventory datasets and rank by criticality.
- For each dataset, define top 3 quality metrics and SLOs.
- Implement baseline checks and gather 30 days of metrics to establish norms.
- Create dashboards and alerting for critical datasets.
- Run quarterly audits to expand the set of rules and metrics.
